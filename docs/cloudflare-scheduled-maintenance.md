# Cloudflare 维护 cron 的失败隔离

## 已确认的问题

迁移分支原 `worker.scheduled()` 在维护分支中顺序执行六项任务，最后用 `finally` 执行普通邮箱和 Agent 收件维护。
前六项中任意一项抛错，其后的中间任务都被跳过。例如身份清理失败时，OAuth 维护、两类发送记录维护、发送附件清理及保留策略本轮都不会执行。
这由实际生产入口的故障注入回归复现，不是从 NAS 或 Cloudflare 线上日志推断出的事故结论。

## 最小修复与不变的边界

`src/scheduled-maintenance.ts` 只拥有维护任务编排；各任务的数据库、对象、权限、期限及去重规则仍由原模块负责。
八项维护按原顺序逐项 `await`，单项失败不会跳过其余任务，不并行、不在本轮重试，不新增任何维护任务。
保留策略仍收到同一个 `controller.scheduledTime`，不因中途失败重新取时间或扩大选集。

每个逃出任务边界的异常只记录固定事件 `scheduled_maintenance_failed` 和固定任务标识，不输出原始异常、URL、凭据或邮件内容。
所有任务尝试结束后，若捕获过这样的异常，仍抛出同名通用错误，使整次 cron 保持失败而非伪报成功。
三个原维护函数自行捕获底层错误：`scheduledOutboxCleanup`、`maintainNormalInbox`、`maintainAgentInbox` 仍保留各自的 `*_cleanup_unconfirmed` 日志和原返回行为。
外层不能汇总被其内部处理的失败；本轮不将这三项改为抛错，也不宣称所有底层错误都能改变 cron 成功状态。
这只能覆盖可捕获的任务异常；平台强制终止、CPU/执行时限、永久未返回的 Promise 或整个数据库不可用不能因此获得完成保证。

每分钟发送/Agent 派发分支保持原样，仍使用原有 guard 和未知结果规则；本修复不重放发送、不更改调度频率或授权策略。
隔离验收候选的空 `triggers.crons` 也保持不变，本地测试调用 scheduled handler 不等于已启用云端 cron。

## 验证与回退

`tests/scheduled-maintenance.test.mjs` 编译并调用真实 `worker.scheduled()`；任务边界由测试构建插件替换，正式 bundle 没有故障开关。
覆盖成功顺序/时间、八个独立边界抛错点、多项抛错、无重试、敏感异常不泄露和每分钟分支兼容；不是这八项真实内部故障的完整模拟。
修复前业务红测为 2/11，通过的两项是成功路径与每分钟分支；其余九项失败现场保留。
此前两次测试夹具构建错误也分别保留，不能当作业务问题复现证据。

完整生产 bundle、真实本地 workerd/D1/R2 的维护与发布候选回归另行执行，不以替换任务的编排单测代替数据生命周期验证。
本轮结果以 `linshi/eesched-1101/verification.json` 的实际状态为准；不是一次全仓测试，也不是云端运行或成本验收。
无 schema、依赖、存储格式或公共 API 变化。回退源码编排即可，不能删除表、对象、历史回执或撤销已发生的清理。
本轮没有提交、推送、合并、云端部署、真实邮件操作或 NAS 变更。
