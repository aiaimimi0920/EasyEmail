# Cloudflare 创建历史与未决结果切片

M3h 为已有分配 guard 增加可查询历史和显式风险确认，使 Web 刷新或重新登录后
仍能核对原记录。它不将未知结果改写成失败，不自动取消、补建或恢复远端资源。

## 1. 历史接口与所有权

以下接口均位于 `/api/v1`：

| 接口 | 权限 | 行为 |
| --- | --- | --- |
| `GET /mailbox-creations` | `mailboxes:read` | 当前用户创建记录，按创建时间、记录 ID 倒序分页 |
| `GET /mailbox-creations?state=unresolved` | `mailboxes:read` | 尚未确认风险的 `pending/unknown` 记录 |
| `GET /mailbox-creations/:id` | `mailboxes:read` | 只读核对当前状态，不访问供应商 |
| `POST /mailbox-creations/:id/acknowledge` | `mailboxes:write` | 记录用户知悉不确定性，不创建新邮箱 |

分页复用 `limit`（1–100，默认 25）和记录 ID cursor。
cursor 的时间锚点也按用户归属查询；其他用户的 cursor 不可用于探测历史。
列表仅接受 `limit/cursor/state`，未知筛选字段拒绝处理。
管理员身份不能绕过邮箱记录归属，Cookie 写入继续校验 Origin。
API Key 的历史读取和确认写入分别受 read/write scope 控制。

安全视图仅包括记录/邮箱 ID、原请求键、供应商 ID、地址、状态、脱敏错误、
创建时间、平台期限、风险确认时间及 `retrySafe:false`。
不返回用户 ID、请求哈希、配置哈希、供应商 endpoint 或任何凭据。
错误码使用明确允许名单；不认识的旧错误仅显示 `creation_unconfirmed`。

## 2. 确认不是取消、失败或解决

确认请求必须准确填写原地址，并显式知悉额外分配的风险：

```json
{"confirmAddress":"ee_example@cf.example.test","acknowledgeUncertain":true}
```

服务端只写入 `acknowledged_at`，首次时间保持不变。
它不修改 `state`、原请求键/哈希、地址、供应商归属、配额、分配计数或冷却。
没有供应商调用，也不会删除 guard、退还累计配额或声明原请求已经取消。
用户确认后，仅解除当前页面的等待；还需另行点击分配才发起新的请求和新的键。

原请求仍可能在上游已成功，或在确认之后才完成。
因此页面必须提示：另起分配可能产生额外邮箱并占用配额。
原状态为 `pending/unknown` 时，重复确认保持同一时间，局部存储故障可安全重试。
确认使用同一个原子 UPDATE 中的状态条件：如果原创建已经变成 `complete`，
返回 `409 creation_state_changed`，要求先核对原结果，而不是确认一个陈旧状态。

确认过的记录仍出现在完整历史中，`pending` 稍后可正常变成 `complete`。
原键仍能回放原邮箱/未知结果，永远不因确认而获得重放远端写入的许可。
这不是远端未知资源的自动认领、凭据恢复、人工修改结果或对账工单系统。

## 3. Web 恢复与分配状态归属

邮箱列表/阅读仍由 `Mailboxes.tsx` 拥有；分配表单移入 `MailboxAllocation.tsx`，
请求/幂等键/未决状态由 `useMailboxCreation.ts` 管理，历史和风险确认界面独立展示。
这是按状态及资源生命周期拆分，不复制第二套分配业务规则。

页面初次载入先读取完整历史的第一页，以及最新未确认风险的记录。
即使该未决记录早于第一页，仍能恢复等待上下文；接口失败时先阻止新分配，
用户可刷新重试，不在无法核对历史时静默发起新的键。
恢复过程仅执行 GET，不自动重发 POST，也不在浏览器存储中保存凭据或原请求。

当前未决记录锁定时，不能通过选择其他创建历史绕过风险确认。
点击“检查创建结果”使用只读详情；如果已经完成，读取并打开实际邮箱。
对同一页面中丢失响应、尚未取得记录 ID 的原请求，仍保留原请求内容和键，
沿用原有显式同键提交/回放机制，不换键或静默换供应商。
完整历史支持分页、打开已完成邮箱，以及再次查看已确认过风险的未决记录。
用户退出后状态随用户组件销毁，另一个用户不会看到上一个用户的历史。
邮箱列表刷新期间禁用旧列表及已选邮箱操作，打开条目时重新读取详情；
从管理页返回或刷新时不以旧缓存的有效期状态暂时启用已经到期的邮箱。

尚未在浏览器整页刷新后恢复“guard 尚未落库”的原始请求内容；
服务端历史只证明已经持久化的 guard，不是所有 HTTP 到达事件的日志。
不能把“当前没查询到记录”当作一个仍在进行的请求永远不会落库的证明。

## 4. 数据兼容与回退

新增 `0010_creation_history.sql`：只为创建 guard 增加可空确认时间和用户/时间索引。
0001–0009 保持不变；旧记录默认未确认，历史供应商归属仍允许 NULL，不猜测补全。
已有用户、会话、邮箱、guard、保留策略及分配观测票据逐列保留。
重复迁移和重启不产生新的外部创建。

旧 Worker 可忽略新增列和索引；回退应使用匹配的旧 Web，保留扩展 schema，
不 DROP 历史或 guard。旧版本没有历史恢复界面，不能宣称混跑时具有完整新语义。
本地开发的产品回退仍是保留原目录和现行部署，不合并迁移分支。
本轮不发布生产、不导入生产邮件或凭据、不自动退役旧服务。
