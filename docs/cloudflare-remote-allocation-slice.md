# W12f1 远端随机地址分配基础

本切片补齐由远端生成地址的创建合同，不新增供应商类型，不代表 M2U 或 ETempMail 已接通。
本地验收以独立 `remote-allocation-final/verification.json` 的实际 `status` 为准；不包含真实供应商创建、真实投递或 Cloudflare 发布。

## 创建与身份

- 旧 `Provider.create(address)` 和精确自定义地址路径保留；新增可选 `createRandom(domain)`，只向该能力传入选定域名。
- 同时实现两种随机创建能力时优先选择远端分配，不能先拟定地址再冒充上游实际返回值。
- 沿用请求 hash、请求键、创建配额、供应商 revision/冷却 fence 和单次写入 guard。
- 远端调用之前只存放不可投递的内部预约，不把预约当邮箱、不发给上游，也不向 API 或网页返回。
- 上游返回地址必须是合法且已规范化的单一 addr-spec，域名必须严格匹配选定域；不接受其他域、空值或宽松猜字段。
- 先原子绑定真实地址，再加密凭据并完成邮箱事务；唯一约束和已有邮箱检查防止跨用户或无 guard 导入邮箱被占用。
- 期限沿用平台限制、已知供应商寿命与实际上游期限取较早值的规则，不从不完整公开文章猜寿命。

## 不确定结果

远端结果未确认时，创建结果和历史返回：

```json
{
  "address": null,
  "addressPending": true,
  "requestedDomain": "remote.example.test",
  "retrySafe": false
}
```

响应丢失、地址非法或本地失败均保留原键记录，不自动重发、不改用精确创建或其他供应商。
地址已绑定而本地提交响应丢失时，响应从持久 guard 核对，不用内存中的旧预约猜地址；重启后的原键仍只读重放。
旧已知地址记录保持原结构；本次没有新增 schema、依赖或锁文件变化。

## 网页与风险确认

地址未知时显示短状态“地址待确认”；刷新、检查创建结果和刷新后恢复不会重新创建。
另起分配需输入原请求键并勾选现有风险确认，API 使用 `confirmRequestKey`。
地址已知时仍必须输入原邮箱地址并使用 `confirmAddress`，不能用请求键降级确认。
确认更新携带原地址 CAS；若确认期间真实地址已绑定则返回 `creation_state_changed`，须刷新后重新核对。
确认不取消在途请求，不把 unknown 改成成功；原请求晚成功后仍可从历史打开真实邮箱。

## 验证范围与限制

`remote-allocation.test.mjs` 覆盖单次调用、实际地址/期限、重启重放、在途核对、未知结果、错误域、地址碰撞、导入邮箱、落库失败、绑定 ACK 丢失和确认竞态。
`remote-allocation-web.test.mjs` 使用真实 Chrome 验证未知地址、刷新恢复、请求键确认、另起分配和晚成功；检查 390px 布局、外站请求及浏览器存储。
测试适配器与数据库故障注入只通过测试 bundle 入口接线，正式 Worker 没有测试 header、供应商类型或开关。
共享创建/历史/Web 的旧供应商、schema 兼容及保留策略回归须在冻结候选上重跑，不能沿用前轮绿测替代本轮验收。

M2U 官方公开资料已读，但创建 JSON、双 Token、实际期限和分页仍需更完整协议证据。
公开应用页面的本地读取遇到 TLS 连接失败；没有据此调用真实创建来猜结构，也没有绕过 custom 的 Turnstile。
M2U、ETempMail 和 Mail2925 仍是后续迁移目标；既有 Mail.tm/TempMail.lol 许可边界不变。
